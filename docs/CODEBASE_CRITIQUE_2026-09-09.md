# ForgeAI Codebase Critique — 2026-09-09

A read-only audit of the repo (602 tracked `.py` files, 2,455 tests,
3,249-line `AGENTS.md`) run via three parallel exploration subagents plus
direct verification (`ruff`, `git`, file reads). Every claim below is backed
by a file:line citation or a measured count.

---

## 1. `AGENTS.md` is a 3,249-line changelog graveyard, not an operating doc

**Evidence**
- 234 `### ` headers; only ~5 are actual operating directives (sections A–E).
  The rest are dated retrospective mini-reports (`#### Refactor 2026-08-30`,
  `#### Boot 2026-09-05`, `R&D Round 26…30`).
- The tail (lines 2950–3249) references files that **do not exist**:
  `research/config.py`, `research/model_loader.py`,
  `research/inference/kv/snapkv.py`,
  `research/keys/quantization/iri_fp4_key.py`,
  `research/checkpoints/ForgeLM_V2_Light.safetensors`. Production code was
  migrated `research/` → `forge/` (commit `f1a7542`) but AGENTS.md was never
  updated.
- Claims "25 canonical keys remain in `research/keys/`" — `research/keys/`
  does not exist; ~37 key files live under `forge/keys/` now.

**Reasoning**: An agent operating doc with stale paths actively misleads
every future session. The actual directives (A–E) are buried under 3,000
lines of history nobody will re-read.

**Fix**
- Split into `AGENTS.md` (≤200 lines: directives A–E + current canonical
  paths + build/test commands) and `docs/CHANGELOG.md` (the dated
  retrospectives).
- Add a "Current canonical layout" section regenerated by a script
  (`scripts/dump_layout.py`) so it can't drift.
- Delete or mark R&D round notes that reference deleted files.

## 2. The headline rule ("Build on the prior, never beside it") is convention-only

**Evidence** — `forge/config.py:996-1009`: `get_config()` does a name
lookup + override. No lineage validation. V12 presets (`forgelm_v12`
line 841, `forgelm_v12_jamba` line 949) are derived by manually spreading
`**MODEL_CONFIGS["forgelm_v2_pro"].__dict__`. V8/V9 have **no preset
entries at all**. The only safety net is
`tests/unit/test_r37_v12_preset.py:134-159` (`test_no_silent_regression`),
which covers V12→V11 only.

**Reasoning**: AGENTS.md section A calls this "non-negotiable," but a
single contributor forgetting the spread operator silently violates it.
Nothing covers V10→V11 or future V13.

**Fix**
- Make presets first-class objects, not dicts: a `Preset` dataclass with a
  `parent: str` field. `get_config()` refuses to register a preset whose
  `parent` doesn't resolve, and asserts every parent key is present unless
  explicitly listed in a `dropped_keys: tuple[str, ...]` field (forcing the
  "document WHY" rule from section A).
- Add a parametrized test walking the full preset DAG for every pair, not
  just V12.

## 3. `ForgeEngine` is a 3,837-line god object (120 methods)

**Evidence** — `forge/engine/forge_engine.py`: 3,837 LOC, 120 `def`, 37
`try:` blocks. `__init__` (lines 281–350) sets 25+ attributes spanning
model, tokenizer, KV cache, decoding, quant, library, tools, profiler,
event log, hotswap, session cache, crash recovery. Single methods span
hundreds of lines: `from_checkpoint` (566+), `activate_optimal` (1410+),
`generate` (2184+), `generate_with_tools` (2639+), `benchmark` (3509+).

**Reasoning**: ≥8 distinct responsibilities in one class. Any change risks
regressions in unrelated subsystems (the 37 try-blocks are a symptom — the
author defensively catches everything because the surface area is
unmanageable). Untestable in isolation.

**Fix** — Extract collaborators (pure move, no behavior change):
- `CheckpointLoader` — `from_checkpoint`, `_load_with_fallback`, metadata.
- `AccelerationManager` — `_apply_quantization`, `_activate_kv_cache`,
  `activate_optimal`, OOM recovery.
- `GenerationRunner` — `generate`, `generate_stream`,
  `generate_with_tools`, sampling wiring.
- `EngineProfiler` — `benchmark`, `diagnose`.
`ForgeEngine` becomes a thin facade. Keep the public API identical; add a
deprecation shim if needed.

## 4. R&D bloat: 26+ quant classes, 14 decoding files — most broken

**Evidence**
- `forge/quant/` (9 files) + `forge/engine/quant/` (13 files) = **26 quant
  classes**, 30+ `quantize_*` entry points. `novel_quant.py` alone has 8
  classes + 20 functions.
- `forge/decoding/` has 14 files (medusa, dspark, eagle, mtp, peagle, uno,
  suffix_decoding, megakernel, …).
- `novel_quant_r44.py`, `r45.py`, `r46.py`, `r48.py` exist but are **not
  imported by `forge_engine.py` at all** (verified) — direct violation of
  AGENTS.md rule E ("versioned filenames fragment the codebase").
- `.devin/scratchpad.md:32-45` (the project's own gap analysis) states:
  **all quant modes are 3.5× slower than unquantized**, `int8` is broken
  (dtype mismatch), speculative/MTP/EAGLE3 decoding all ERROR,
  `prefix_cache`/`cuda_graph`/`compile` all ERROR.

**Reasoning**: 50+ quant/decoding variants that don't work on the target
hardware, while the scratchpad explicitly says the root cause is "naive
dequantize-then-matmul, no fused quantized GEMM kernels." Adding a 27th
quant class before fixing the existing 26 inverts AGENTS.md section C
("No area is 'solved'") — the rule is read as "add more variants," not
"make the existing ones actually fast."

**Fix** (priority order)
1. **Stop adding quant variants.** Freeze new quant R&D until existing
   ones hit parity with unquantized throughput.
2. **Delete `novel_quant_r44.py`–`r48.py`** (unreferenced) or fold working
   bits into `novel_quant.py`. Rule-E violation.
3. **Fix the root cause**: implement FP8/NVFP4 via `torch._scaled_mm`
   (Blackwell native) and int8 via a proper fused path. One working quant
   mode beats 26 broken ones.
4. **Fix the decoding API mismatch**: scratchpad lines 51-53 show
   `generate()` passes `min_p` but MTP/EAGLE3 don't accept it. 5-minute
   fix sitting unfixed — violates rule B ("Never leave a known bug
   sitting").
5. **Gate dead variants behind a registry**: `QUANT_REGISTRY` only
   exposes methods that pass a throughput-parity test. Untested variants
   stay unregistered.

## 5. `tests/integration/` is empty — no real integration suite

**Evidence** — `tests/integration/` contains only `__init__.py` and a
`.forge_recovery` dir. Zero `def test_`. `tests/conftest.py:65-92` builds
a full `ForgeEngine` and calls `activate_optimal()` for "integration
tests" that don't exist. 2,416 unit tests, 39 evolution tests, 0
integration.

**Reasoning**: Unit tests verify components in isolation, but the
scratchpad shows the real bugs are at the integration boundary
(quant+KV+decoding+compile interacting). With no integration tests, every
scratchpad regression was found manually. This is why commits bundle "10
P0/P1 bottlenecks" — there's no safety net catching them earlier.

**Fix**
- `tests/integration/test_end_to_end_generate.py`: load `forgelm_v2_light`,
  run 50-token generation, assert tok/s > baseline and no error.
  Parametrize across each registered quant mode and KV strategy — would
  catch every scratchpad failure automatically.
- `tests/integration/test_quant_parity.py`: assert each quant mode is
  within 1.2× of unquantized throughput (the 3.5× regression becomes a
  failing test, not a scratchpad note).

## 6. 447 `except Exception` handlers, many silently swallowing errors

**Evidence** — 337 in `forge/`, 110 in `forge_gui/`. Examples with
`pass`/`continue`/`return None`:
- `forge/engine/forge_engine.py:405,409,439` (`__del__`,
  `_release_acceleration_resources`)
- `forge/model_loader.py:2761,3674,3769`
- `forge/training/runners/sft_train.py:257` (`except Exception: continue`
  — silently drops training data)
- `forge/self_play/discovery/qwen_adapter.py:276`
  (`except Exception: obj = None`)

**Reasoning**: `except Exception: pass` is the worst pattern in a research
codebase — it turns hard failures into silent wrong results. The sft_train
one (line 257) means corrupted training rows are silently skipped with
only a counter, no log of *which* row or *why*. When training quality is
the whole point, this is dangerous.

**Fix**
- Replace `except Exception: pass` with `except Exception:
  logger.debug(...)` at minimum so failures are visible at DEBUG level.
- For the sft_train data loader: log the offending path + exception, add a
  `--fail-fast` flag so corruption is visible during dev.
- Enable ruff `B904` (currently ignored in `pyproject.toml:71`).
  Re-enable and fix incrementally.

## 7. 1,073 `print()` calls in `forge/` — library code shouldn't print to stdout

**Evidence** — 1,073 `print(` in `forge/` (507 in `forge/engine/` subtree
alone). Examples: `sft_train.py:245,284,330,1145`, `model_loader.py`,
`forge_engine.py`. `forge_gui/api/` has 0 (correct — someone learned the
lesson but didn't propagate it).

**Reasoning**: Library code that prints to stdout breaks any host that
captures stdout (the GUI, server, tests). It also can't be filtered by
log level.

**Fix**
- Replace with `logging.getLogger(__name__)`. Mechanical pass:
  `print(f"Warning: ...")` → `logger.warning(...)`, `print(f"  {path}:
  ...")` → `logger.info(...)`.
- Add a ruff/custom-check banning `print(` in `forge/` (T001 from
  `flake8-print`, or a grep CI step).

## Meta-problem

The project has strong *written* discipline (AGENTS.md sections A–E are
excellent rules) and weak *enforced* discipline. Every rule is convention
+ maybe one test. The result is exactly what you'd predict: rules that
are easy to follow (don't commit safetensors — gitignored ✓) are
followed, and rules that require tooling (preset lineage, no versioned
filenames, no dead keys, fix-known-bugs) are violated in the gaps where no
automated check exists.

**Highest-leverage fix**: make the existing rules machine-enforced — a
preset-lineage validator, a `ruff` pre-commit gate, an integration test
that runs every registered quant/decoding mode, and a "dead key" CI
check. That converts already-good written rules into actual guarantees.

**Second-highest-leverage fix**: stop adding quant/decoding variants and
make the existing ones work — the scratchpad's own benchmarks show 3.5×
slowdowns and outright errors across the board. One fast, correct quant
mode is worth more than 26 broken ones.

## 12. `sft_train.py:main()` is a ~1,360-line monolith

**Evidence** — `forge/training/runners/sft_train.py` is 2,141 LOC with 16
helper functions, but `main()` (line 779 → end ≈ 1,363 lines) does
argparse, model loading, BitNet/NanoQuant conversion, LoRA injection, data
load/tokenize/pack, optimizer setup, EMA/QK-Clip, the SGD step loop, data
augmentation, reward weighting, FreeToken overlap, elastic grad-accum,
EMA update, checkpoint save, NaN guard, logging, validation, and final
export — all in one function.

**Reasoning**: This is the same god-function anti-pattern as
`ForgeEngine`. A 1,360-line `main()` cannot be unit-tested, and any edit
risks breaking an unrelated phase. The helpers exist but `main()` still
orchestrates everything inline.

**Fix** — Split into `build_model(args)`, `build_optimizer(model, args)`,
`build_datasets(args)`, `train_step(...)`, `validate(...)`, `export(...)`,
with `main()` as a thin orchestrator calling them in sequence. Each piece
becomes independently testable.

## 13. Silent training-data corruption at `sft_train.py:257`

**Evidence** — `forge/training/runners/sft_train.py:255-259`:
```python
try:
    obj = json.loads(line)
except Exception:
    n_skipped += 1
    continue
```
Only a per-file aggregate `n_skipped` count is reported at line 284. No
row number, no exception class, no content preview, no validation of the
parsed object shape.

**Reasoning**: When training quality is the entire point of the project,
silently dropping corrupted rows with no diagnostic is dangerous. A
systematic data corruption (wrong encoding, truncated file, schema drift)
would manifest as "model got worse" with no trace back to the data loader.

**Fix** — Log the file path, line number, exception class, and a truncated
content preview at WARNING level. Add a `--strict-data` flag that raises
on the first malformed row. Track `n_skipped` per *error class* so patterns
are visible (e.g. "47 JSON decode errors, 3 missing 'messages' key").

## 14. Custom LoRA stack duplicates PEFT instead of extending it

**Evidence** — `forge/training/bitnet_lora.py` (499 LOC) defines a custom
`LoRAAdapter` (line 232) because PEFT can't inject into the custom
`BitNetLinear`/`NF4Linear`/`ForgeQuantLinear` modules. Parallel adapter
classes exist: `DLoRAAdapter` (`dlora.py`), `DoRALinear` (`dora.py`),
`ForgeAdapter` (`forge_adapter.py`), `AdaLoRAClass` (`adapter_variants.py`).
The user just edited line 350 to add `ForgeQuantLinear` to the merge
check — a manual string-match against class names.

**Reasoning**: Five parallel adapter implementations with no shared base
class or interface. The merge logic at line 350 matches by **class name
string**, so adding a new quantized linear requires manually editing this
tuple — exactly the bug that just happened (ForgeQuantLinear was missing).
This is fragile and will recur.

**Fix** — Define a `QuantizedLinear` mixin/protocol with a
`merge_lora()` method. The merge loop checks `isinstance(module,
QuantizedLinear)` instead of a string tuple. New quantized linears
register automatically. Consolidate the 5 adapter variants behind a
common `Adapter` ABC if their logic overlaps.

## 16. `model_loader.py:build_model_fast` is a 440-line god function

**Evidence** — `forge/model_loader.py` is 3,437 LOC, 80 defs, 9 classes.
`build_model_fast` (line 2975) spans **440 lines** — it builds the
embedding, every layer (attention + FFN + KV cache wiring), the norm,
the LM head, loads checkpoints, applies quantization, and handles
fallbacks. Other large functions: `_forward_impl` (259 lines, line 2121),
`__init__` of the main model (236 lines, line 1718), attention `forward`
(217 lines, line 1087).

**Reasoning**: `build_model_fast` is the canonical model construction
path, and it's a single 440-line function doing 6 distinct jobs. This is
the model-loader equivalent of the `ForgeEngine` god object. Any change
to one phase (e.g. how FFN is built) risks the others.

**Fix** — Extract `_build_embedding(config)`, `_build_layers(config)`,
`_build_head(config)`, `_load_checkpoint(model, path, config)`,
`_apply_post_load_quant(model, config)`. `build_model_fast` becomes a
20-line orchestrator.

## 17. Import-time global side effects in `model_loader.py`

**Evidence** — `forge/model_loader.py` lines 16–34:
- `os.environ.setdefault("SAFETENSORS_FAST_CUDA", "1")` (line 16)
- Triton/Inductor cache dir overrides (lines 23–26)
- `torch.set_float32_matmul_precision("high")` (line 30)
- `torch.backends.cuda.matmul.allow_tf32 = True` (line 32)
- `torch.backends.cudnn.allow_tf32 = True` (line 34)

Also `forge/__init__.py:22-26` calls `cleanup_orphaned_tmp()` at import
time (filesystem side effect on `import forge`).

**Reasoning**: Importing a library should not mutate global torch/env
state. This makes `import forge.model_loader` non-idempotent and
non-composable — a user who wants `float32_matmul_precision("highest")`
silently gets overridden. The filesystem cleanup on `import forge` can
race or fail in read-only environments.

**Fix** — Move all env/torch global mutations into an explicit
`forge.runtime.configure()` function the user opts into. `import forge`
should be side-effect-free. The GUI/server entrypoints call `configure()`
explicitly.

## 18. GUI: no process cleanup on window close — zombie subprocess risk

**Evidence** — `forge_gui/api/process_manager.py`:
- `kill_proc()` (line 63) calls only `self._proc.terminate()` (line 67) —
  no `kill()` fallback, no timeout on `wait()`.
- `ProcessManager` has no `shutdown()` or `kill_all()` method.
- `MainWindow.closeEvent()` (`forge_gui/app.py:398`) stops `GpuPoller`
  and shuts down `EngineRuntime` but **never stops or waits for live
  `ProcessManager` workers**.

**Reasoning**: If a training subprocess ignores `terminate()` (common on
Windows for processes in a syscall), the `QThread` blocks in `wait()`
(line 94) and the subprocess outlives the GUI. Over a session of
launch/quit cycles, this leaks zombie processes.

**Fix** — Add `ProcessManager.shutdown()` that terminates, waits with a
timeout, then `kill()`s all live workers. Call it from
`MainWindow.closeEvent()`. Add a `kill()` fallback in `kill_proc()`.

## 21. `forge/evolution/` is 16,183 LOC, 44 files — and not wired into training

**Evidence** — `forge/evolution/` is 44 `.py` files, ~16,183 LOC. It
implements a full evolutionary optimizer (`ForgeEvolve` class,
`engine.py:149`) with `GeneratorPopulation`, `SurrogateModel`,
`MapElitesArchive`, `FindingsDB`. But: **no import of `forge.evolution`
from `forge/training/`, `forge/engine/`, or `forge_gui/`**. The only
callers are `tests/evolution/` and `tests/unit/`.

8 `# evolution-discovered` comments exist in production code
(`sft_train.py:920,998`, `infinite_loop.py:92,93,106,108`, `config.py:403`,
`hybrid_offload.py:243`, etc.) — but these are hardcoded constants with
no link back to the evolution system that produced them.

**Reasoning**: 16K LOC of evolutionary optimization infrastructure that
isn't connected to the training pipeline it's supposed to optimize. The
`evolution-discovered` constants are frozen snapshots — if the evolution
system finds something better tomorrow, nothing in production updates.
This is a research toy masquerading as infrastructure.

**Fix** — Either:
(a) **Wire it in**: add a `forge evolve --apply-best` command that reads
`forge_evolve.db` and writes the best config to a versioned
`forge/evolution/best_configs.json` that `sft_train.py` loads. Make the
link live, not frozen comments.
(b) **Or shrink it**: if evolution isn't going to be auto-applied, move
`forge/evolution/` to `research/evolution/` and mark it experimental. 16K
LOC of unused optimizer is dead weight in the production package.

## 22. No evidence evolution has beaten manual tuning

**Evidence** — The only "evidence" is 8 `# evolution-discovered` code
comments with hardcoded values (e.g. `ft_focal_gamma = 4.93`,
`prefetch_depth = 7`, `alpha=0.999`). Tests (`test_forge_evolve.py:28-229`)
only compare evolution vs. random/grid search on a `SyntheticDomain` and
a `QuantDomain` simulator — not real training. The test asserts
`>= 0.80 * random_best`, a low bar. No persisted benchmark artifact
compares an evolution-discovered config against a manual one on real
training loss or downstream task performance.

**Reasoning**: "Evolution-discovered" comments carry authority they
haven't earned. A reader assumes these values were validated, but there's
no reproducible artifact. If the evolution simulator's score doesn't
correlate with real training quality, these constants could be worse than
manual defaults.

**Fix** — Before trusting any `evolution-discovered` constant, produce a
reproducible benchmark: run `sft_train.py` with the evolved value vs. the
default, measure val loss, commit the result to

## 25. Cross-thread `ForgeEngine` hand-off in the GUI

**Evidence** — `forge_gui/api/engine_runtime.py:146`:
`_LoadWorker` (a `QThread`) constructs a `ForgeEngine` in the worker
thread and delivers it to the main thread via
`finished_ok.emit(engine, info)`. The engine carries CUDA/torch state
allocated in the worker thread's context.

**Reasoning**: PyTorch CUDA tensors are tied to the device, not the
thread, so this *usually* works. But CUDA streams, cuDNN handles, and
torch.compile caches can have thread-affinity assumptions. Moving a
fully-constructed engine across threads is a known source of subtle
"device-side assert" / "invalid configuration" errors that only
manifest under load.

**Fix** — Either construct the `ForgeEngine` on the main thread (with
the heavy load done in a worker that returns a config/path, not an
engine), or document explicitly that this cross-thread hand-off is
tested and safe. At minimum, add a test that loads a model in a worker
thread and then runs `generate()` on the main thread to catch
thread-affinity bugs.
